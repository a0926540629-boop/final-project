📌 專案摘要（Abstract）

本專案以工業界標準軟體開發生命週期（SDLC）為骨架，完整落地需求工程、UML建模、架構設計、模組解耦、單元/整合/回歸測試、版本控管、程式碼品質檢查、文件撰寫與上台驗證全流程。
專案採用分層架構搭配策略模式實現低耦合、高內聚的設計目標，遵循SOLID設計原則，隔離介面、業務邏輯、資料持久化與通用工具層。
版本管理採用標準 GitFlow 分支模型，搭配 Conventional Commits 提交規範、Pull Request 強制審核機制，模擬正式團隊多人協作流程，可追溯每一次需求變更、bug修復與重構紀錄。
相較於單純「寫出可執行程式」的實作，本專案核心重點在軟體品質、可維護性、可測試性、可擴充性，驗證軟體工程方法論在小型應用系統的落地可行性。

🎯 需求工程（Requirements Engineering）

1. 使用者故事 User Story（INVEST原則）

1. 作為開發者，我希望系統有分層日誌，方便除錯與追蹤執行流程，不影響正式環境效能

2. 作為使用者，我希望輸入參數自動驗證，遇到非法輸入時給明確錯誤訊息，而不是直接崩潰

3. 作為維護者，我希望核心演算法抽離成獨立策略，日後替換演算法不用修改主流程

4. 作為測試人員，我希望功能模組獨立，可單獨撰寫單元測試，不需要依賴完整系統

5. 作為團隊成員，我希望Git提交有統一規範、分支明確，避免版本衝突與難以閱讀的提交紀錄

2. 功能性需求 FR

• 參數校驗模組：空值、型別、邊界值驗證，拋出標準化自訂例外

• 策略排程模組：可動態切換多種演算策略，執行對應業務邏輯

• 持久化模組：支援JSON檔案存取，隔離資料層，後續可無痛替換成SQLite

• 日誌模組：分級 Log（DEBUG / INFO / WARN / ERROR），可透過設定檔開關除錯模式

• 測試介面：提供單元測試入口，獨立驗證各函數輸出結果

• 版本資訊模組：讀取專案版本號、建置時間，方便識別交付版本

3. 非功能性需求 NFR

• 效能：單次演算響應時間 < 500ms；大量輸入時優先保障穩定性，而非極致速度

• 可靠性：核心模組錯誤捕捉，例外不向上傳遞造成整個程序崩潰

• 可移植性：不依賴作業系統特定API，只要有Python3環境即可執行

• 可維護性：程式圈複雜度控制在10以內，變數與函數名採敘述式命名

• 可擴充性：新增演算法只需新增策略實作，不需要修改主流程（符合開放封閉原則）

• 安全性：不直接暴露原始輸入給底層儲存，做輸入過濾，避免注入風險

• 可審計性：重要操作留下日誌，方便事後追溯問題

4. 用例（Use Case）文字描述

• UC01：系統啟動 → 載入設定、初始化日誌、註冊可用策略

• UC02：使用者輸入資料 → 參數驗證，失敗回傳錯誤；成功交給業務層處理

• UC03：執行演算策略 → 根據設定選取對應演算法，回傳結果

• UC04：資料儲存/讀取 → 透過DAO層存取持久化檔案

• UC05：執行測試套件 → 跑單元測試，輸出測試報告

🧠 設計準則與設計模式

本專案嚴格遵守 SOLID 五大設計原則：

1. SRP 單一職責：一個類別/函數只負責一件事

2. OCP 開放封閉：對擴充開放、對修改封閉，新增策略不用動主程式

3. LSP 里氏替換：所有策略子類別都可以替換抽象策略父類別

4. ISP 介面隔離：不強迫實作不需要的介面方法

5. DIP 依賴反轉：高層模組依賴抽象介面，不依賴具體實作
主要採用設計模式：策略模式 Strategy Pattern
次要導入：簡單工廠模式、單例模式（日誌器）

📜 版本控制策略｜標準 GitFlow

分支定義：

1. main：生產穩定分支，永遠可執行，禁止直接push，只能透過PR合併，合併後打版本tag（v1.0.0、v1.1.0）

2. develop：整合開發分支，所有功能完成後先合併到這裡做整合測試

3. feature/*：新功能分支，從develop開出，例如 feature/add-logger

4. release/*：發布準備分支，從develop開出，最後測試、修小bug，合併main與develop

5. hotfix/*：緊急修復分支，從main開出，修完同時合併main與develop

Commit 規範 Conventional Commits

格式：type(scope): message

• feat：新增功能

• fix：修復bug

• docs：文件修改（README、註解）

• refactor：重構程式，行為不變

• test：新增/修改測試

• style：排版、命名、格式調整，不影響邏輯

• chore：建置、依賴、設定檔調整

範例：
feat(strategy): 新增排序演算策略
fix(dao): 修正json寫入時編碼錯誤
refactor(utils): 抽離驗證函數
docs: 更新架構圖與需求說明
PR 審核規則

• 至少1人Review後才可以合併

• 合併前必須跑通全部測試

• 提交紀錄要乾淨，禁止大量WIP雜亂commit

🧪 測試策略｜測試金字塔
測試金字塔：單元測試最多 → 整合測試次之 → E2E端到端測試最少
1. 單元測試（Unit Test）：針對每一個獨立函數、策略類別，隔離依賴，驗證輸入輸出，使用pytest，目標核心邏輯覆蓋率 ≥80%

2. 整合測試（Integration Test）：測試多模組串接，例如Service呼叫Strategy再呼叫DAO，確認資料流正常

3. 回歸測試（Regression Test）：新增功能、重構之後，完整跑一遍舊測試，避免引入退化bug

4. 邊界測試：極限值、空輸入、錯誤型別、超大輸入等負面案例

測試輸出：測試通過率、覆蓋率報告、失敗案例詳細堆疊資訊。

✅ 程式碼品質規範

• 語言規範：Python PEP8

• Linter：flake8 檢查語法、命名、排版

• 變數命名：snake_case；常數全大寫；類別 PascalCase

• 註解：複雜演算法、商業規則寫Docstring；簡單邏輯不用多餘註解

• 禁止：魔法數字、長函數、深層巢狀if、重複程式碼

• 重構觸發條件：重複程式、圈複雜度過高、難以閱讀、難以測試

⚠️ 風險評估與應對對策
風險項目 風險等級 影響說明 解決方案 
模組整合時出現介面不相容 中 單獨跑都正常，串起來報錯 定義明確DTO，先寫介面合約，再實作；小步整合 
時程落後、來不及做完所有擴充功能 高 期末無法交付完整版本 優先完成核心流程，次要功能標記為後續擴充 
測試案例不足，上線後才發現bug 中 穩定性下降 開發功能同時寫測試，TDD思維優先寫測試再寫程式 
Git協作衝突大量發生 中 浪費時間解衝突 小commit、頻繁pull；大型功能拆成小分支 
效能不如預期 低 大量資料處理緩慢 先正確再最佳化，用profile工具找出瓶頸，不預先優化
